# Context maintenance

`retro context [path]` reviews the named instruction file, skill, or project instruction set. Default to that project's root instruction file when no path is given. This mode replaces the session source/candidate/report steps, while retaining retro's tune load and read-only transcript handling. It does not turn every small task into a full instruction inventory.

## 1. Pin the scope and sources

Record the requested scope, existing authorization, and inspected revisions or immutable working-text snapshots. Preserve broad uncommitted changes in that baseline. Inventory authoritative policies, thin harness shims, linked references, skills, and actual mechanical enforcement within the scope. Name their loading paths and owners.

Inspect current files before asking about facts available there. Check relevant paths, command caveats, changed referents, and enforcement wiring. Record which facts were inspected and which remain unverified. Completion means every in-scope source and its loading route is accounted for; expand scope only when authorized.

## 2. Diagnose the cause

Use observed incidents, raw transcript evidence, current files, and enforcement results. Check existing guidance before adding an instruction. A single high-consequence failure can justify action; recurring context cost for low-consequence observations needs sufficient evidence. History mode's recurrence rule still governs inferred preferences; an explicit user instruction is already authoritative.

| Cause | Remedy to propose |
|---|---|
| Missing information | Supply the needed fact at its point of use |
| Failed retrieval | Repair the pointer or loading trigger to existing guidance |
| Ambiguous wording | Clarify the same intent and test the differing interpretations |
| Known rule skipped | Test adherence under the observed pressures |
| Stale fact | Update from the current referent with revision evidence |
| Contradiction | Identify authority and resolve the owner-held decision |
| Missing enforcement | Add or repair a check for a mechanical violation; retain uncovered guidance |

An instruction set with no supported finding may need no change. Successful recent sessions do not establish that a protective rule is unnecessary.

## 3. Account for preservation

Apply tune's `PRESERVATION.md` (directly linked from retro's `SKILL.md`): its ledger, dispositions, and retirement evidence cover every meaningful instruction each proposal touches. Completion means every proposed edit has a disposition and no unaccounted meaning loss.

## 4. Propose and apply within authority

Present ranked itemized findings with source evidence, cause, remedy, destination, ledger rows, and a draft eval case following retro's report contract. Distinguish observed defects from hypotheses. For relocation, report `PRESERVATION.md`'s three assurance checks separately; unavailable coverage stays unrun.

Apply the changes the user selects through tune. The user's existing explicit direction can already authorize those selections; do not ask again for the same scope. Resolve new owner-held policy changes before dependent edits. Retiring an instruction does not authorize deleting code, data, worktrees, or historical evidence.

## 5. Retain revision provenance

Record the outcome as `PRESERVATION.md` says, adding step 1's scope inventory, and mark each change proposed, implemented, verified at its stated boundary, rejected, or unrun. Keep immutable baseline evidence after the current instructions change.

Completion means all affected instructions have dispositions and every claimed preservation or retirement has the named evidence. Report missing assurance explicitly; do not promote a wording edit or static link check into a behavioral result.
